### TD-05：三处报表各自重写库存公式 {#td-05}

**人话解释：**
"这个 SKU 现在有多少可用库存"这个算法（现有库存 − 已预留 = 可用），Forecast（未来库存预测）、Aging（逾期预留预警）、Factory CSV（缺货导出）这三个功能各自写了一遍同样的计算逻辑，而不是三个功能都去调用同一个已经写好的函数。现在三处结果碰巧完全一致，但只是因为没人动过其中一处——以后如果要改算法（比如"报价阶段的预留不算进去"），必须记得三个地方都改，漏改一处就会出现三个报表数字对不上的情况。

**涉及文件：**
- `src/app/(portal)/inventory/page.tsx`（Forecast 模式）
- `src/lib/reservation-aging.ts`（Aging 逾期预警）
- `src/lib/shortage-report.ts`（Factory CSV 缺货导出）

**已存在但没被充分使用的东西：**
`src/lib/inventory.ts` 里的 `getStock()` 函数已经实现了正确的公式，但目前**只有 SKU 详情页在用**，上面三个报表都没调用它，是各自重新写的。

**触发条件：** 下次有人改动库存公式相关逻辑（比如调整预留口径、增加新的库存状态）时，如果只改了 `getStock()` 或只改了某一处报表，就会产生数字不一致。目前三处仍然一致，风险是"潜伏"而非"已发生"。

**修复方案：** 在 `src/lib/inventory.ts` 加一个批量查询版本（按仓库 + 一批 SKU 一次查，避免逐个查询效率低），让三个报表都改成调用它，而不是各自 `groupBy`。

**状态：** 已登记，未修复
**登记日期：** 2026-08-17

### TD-06：Dashboard 低库存卡片多仓统计错误 {#td-06}

**人话解释：**
仪表板首页的"低库存预警"卡片，在统计每个 SKU 的可用库存时，**没有按仓库分开算**，把 Brisbane 和 Sydney 的库存混在一起加总。如果一个 SKU 在 Brisbane 缺货但 Sydney 有货，这个卡片可能显示"库存正常"，掩盖了 Brisbane 真实缺货的情况；反过来也可能把两边库存混算出一个不代表任何单一仓库真实状态的数字。

同时，预留数量的统计也没有过滤掉"预留数量为 0 或负数"的记录，虽然目前看没造成实际错误（因为为 0 的记录不影响求和），但和其他报表的过滤逻辑不一致，属于潜在隐患。

**涉及文件：**
- `src/app/(portal)/dashboard/page.tsx`（低库存卡片的查询逻辑，约第 88-103 行区域）

**触发条件：** 已经是现在进行时的 bug，不需要额外触发条件——只要店铺是多仓（Brisbane + Sydney 都有库存的 SKU），这个卡片现在就可能显示错误数字。

**修复方案：** 查询时按 `locationId` 分组统计，而不是把所有仓库混在一起加总；预留数量查询补上过滤条件，和 TD-05 的批量函数统一后一起修复更省事。

**状态：** 已登记，未修复（建议优先级高于 TD-05，因为这是已发生的错误，不是潜在风险）
**登记日期：** 2026-08-17
